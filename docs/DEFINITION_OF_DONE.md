# R1 packet Definition of Done

**Status rule:** Every packet remains **In progress** until every applicable checkbox below is checked and its evidence is linked. A human, device, credential, backup, or owner approval dependency is a blocking prerequisite—not a waiver and not a code-completable checkbox. Do not mark a packet complete based on planned work, a compile-only result, a different commit SHA, or synthetic evidence presented as real-world evidence.

## Universal PR checklist — required for every packet

- [ ] Success path tested.
- [ ] Failure path tested, with fault injection at every durable write step and proof of atomic rollback/no partial state.
- [ ] Restart and recovery tested: persist, kill/force-stop, reopen, and compare relevant state hashes/read-back values.
- [ ] Integration with dependent modules tested.
- [ ] Required checks green on the exact release/PR head SHA; link the workflow run and record the SHA.
- [ ] Any unchecked box keeps the packet **In progress**.

Each PR must state the packet number, scope, dependencies, acceptance evidence, exact tested SHA, known limitations, and external blockers. Never carry evidence forward to a new SHA without rerunning the required checks.

## Packet 1 — Governance

- [ ] Branch protection/rulesets applied to `main` and `release/*`: required checks, at least one approving review, no force-push, no branch deletion, and rules applied to administrators.
- [ ] Direct push and force-push rejection attempts performed; exact rejection output saved in the PR. Do not claim this gate if repository-admin permissions prevent the attempts.
- [ ] Every relevant workflow trigger includes native Java/Kotlin template paths.
- [ ] Java-template-only PR opened and workflow execution evidenced.
- [ ] `STATUS.md` generated by workflow from actual run/check results, including commit SHA, per-gate pass/fail, and evidence links. Hand-maintained status claims removed.
- [ ] Release-tag workflow verifies the tagged SHA has every required check green and fails closed for missing, pending, cancelled, or failed checks.
- [ ] CI test asserts `uiCutover`, sync, and payment/gateway flags default OFF.
- [ ] Negative test proves a tag pointing at a red SHA is refused.
- [ ] Exit evidence attached: rejected-push logs, Java-only triggered run, generated `STATUS.md`, and refused red-SHA tag.

**External blocker:** repository administrator token/permissions are required for branch protection and rejection verification. A 403 is a blocker, not a pass.

## Packet 2 — Financial diagnostic

- [ ] Database is opened read-only by construction; test proves no database writes occur.
- [ ] Detects duplicate payments, orphan payments, missing booking references, negative balances, overpayments, disagreement among `p`, `pays[]`, and `payments[]`, and receipt/daily-total mismatches.
- [ ] Unparseable or ambiguous records fail loudly and are enumerated; no silent skipping.
- [ ] Strict mode exits non-zero for every unresolved finding.
- [ ] Redacted report replaces names, phone numbers, and IDs with stable hashes.
- [ ] Automated planted-PII test greps all emitted output and proves no planted PII leaks.
- [ ] Fixture tests cover each finding and malformed/ambiguous input.
- [ ] Run completed against an owner-authorized real backup; record backup provenance and checksum without exposing sensitive data.
- [ ] Accounting owner written sign-off attached to the PR.

**External blockers:** authorized real backup and accounting owner's written sign-off. Until both exist, Packet 2 is **Blocked/In progress** even if fixture tests pass.

## Packets 3–6 — Persistence domains and financial journal

For each domain packet (settings, rooms, guests/bookings, inventory/expenses/restaurant) and for the journal:

- [ ] Full create/read/update/delete or domain-appropriate lifecycle operations work through the canonical repository; posted financial entries remain append-only.
- [ ] Zod/schema validation rejects invalid input at the repository boundary.
- [ ] Foreign keys are enforced; a booking cannot reference a missing room or guest.
- [ ] Shadow comparison against legacy data reports zero unexplained mismatches over approved representative data.
- [ ] Rollback drill completed and evidence attached.
- [ ] Identical repository contract suite passes on IndexedDB and Android SQLite.
- [ ] Legacy source data is preserved and quarantined; no deletion in these packets.
- [ ] Promotion is domain-scoped and authority flags remain OFF until that domain's gate is accepted.

### Additional journal requirements

- [ ] Amounts stored as integer paise with explicit ISO currency.
- [ ] Journal is append-only; corrections use reversal/compensating entries, never edits/deletes.
- [ ] Idempotency key enforced per command at the transaction boundary.
- [ ] Balances, receipts, and daily reports are deterministic projections of the journal.
- [ ] Randomized operation-sequence tests prove projected balance equals journal sum.
- [ ] Concurrent duplicate-command test proves exactly one posting.
- [ ] Fault injection/kill at every write step proves no partial journal, folio, audit, or outbox state.
- [ ] All DB writes commit atomically; no network or other non-DB await occurs inside a DB transaction.
- [ ] UI success is emitted only after durable commit and read-back where required.

## Packet 7 — Android emulator instrumentation

- [ ] CI emulator instrumentation executes against real SQLite.
- [ ] SQLite full-disk/storage-exhaustion behavior tested.
- [ ] Transaction rollback tested for failures at every write step.
- [ ] Schema migration and migration rollback tested.
- [ ] Process kill during transaction tested; reopen proves all-or-nothing state.
- [ ] Results and APK/build identity linked to the exact tested SHA.

## Packet 8 — Physical-device qualification

- [ ] Two physical Android devices tested, including one low-end device.
- [ ] Install and upgrade with seeded data tested.
- [ ] Airplane/offline mode, low storage, force-stop, and reboot tested.
- [ ] Keystore and biometric behavior tested on hardware.
- [ ] `QUALIFICATION.md` records device model, Android version/build, APK SHA, each case/result, and evidence (logs/screenshots).
- [ ] Restart/recovery and data integrity verified after each destructive/fault scenario.

**External blocker:** the two physical devices and operator-run evidence. Emulator evidence cannot substitute.

## Packet 9 — Security and recovery

- [ ] PIN lockout and retry limits tested, including restart and clock manipulation where applicable.
- [ ] Offline recovery-key flow restores access without server/SMS dependency.
- [ ] Test proves SMS/OTP alone cannot recover, replace, or unwrap the data-encryption key.
- [ ] Backup/restore tested and backup inspection proves no plaintext sensitive data exposure.
- [ ] Automated log grep proves no sensitive data is emitted.
- [ ] Authorization, tamper, key rotation/lifecycle, failure and recovery paths tested end-to-end.

## Packet 10 — Offline end-to-end acceptance

- [ ] Automated offline workflow completes booking → check-in → charge → payment → check-out → daily report.
- [ ] Report totals equal journal-derived totals.
- [ ] App/process restarted; workflow state and report totals re-asserted.
- [ ] Failure/recovery and duplicate-command cases included.
- [ ] Workflow runs on the supported persistence implementations and exact candidate SHA.

## Packet 11 — Release candidate

- [ ] Reproducible build: same source SHA and declared toolchain produce the same unsigned APK hash.
- [ ] APK signed using the owner's signing key; key remains owner-controlled and is never committed or disclosed.
- [ ] Package ID, permissions, exported components, and feature-flag defaults verified from the built artifact.
- [ ] Upgrade test from the previous approved build preserves seeded data and passes recovery checks.
- [ ] Security and required CI checks green on the exact tagged SHA.
- [ ] Owner approval recorded in the release PR.
- [ ] Release artifact SHA, signing identity/fingerprint, build provenance, and test evidence recorded.

**External blockers:** owner-controlled signing key and explicit owner approval. No release or publishing without them.

## Global release invariants

- R1 is local-first. Gateway collection, Pay Bridge dispatch, cloud sync, and global `uiCutover` remain OFF/excluded.
- Financial journal is the source of truth; balances and reports are projections.
- No legacy data deletion in the same release as migration/promotion.
- Real-data, physical-device, sign-off, and signing gates require real evidence from the responsible people; never simulate them.
- A passing test proves only the behavior and environment it actually exercised.
